# План разработки: Get-Git — выгрузка и обновление репозиториев корпоративного GitLab

## 1. Назначение

Настольное Windows-приложение (Python) для read-only зеркалирования доступных пользователю
репозиториев корпоративного GitLab в локальную директорию.

- Доступ к git — по SSH-ключу; список репозиториев — через GitLab REST API (personal access token, право `read_api`).
- Первый запуск — полное клонирование; далее по кнопке «Обновить» — только изменения.
- «Обновить» = полная синхронизация: локальные ветки жёстко приводятся к состоянию сервера,
  удалённые на сервере ветки удаляются локально. Коммит/пуш не предусмотрены.

## 2. Технологический стек

| Компонент | Выбор | Обоснование |
|---|---|---|
| Язык | Python 3.12+ | требование |
| GUI | **PySide6 (Qt 6)** | нативный вид на Windows, готовые QTableView/сигналы/потоки, официальная LGPL-лицензия, хорошо собирается PyInstaller |
| Git-операции | системный `git.exe` через `subprocess` | полный контроль над SSH (`GIT_SSH_COMMAND`), никаких лишних зависимостей; GitPython всё равно требует git.exe |
| GitLab API | `requests` (прямые вызовы REST v4) | нужны 2–3 эндпоинта, полноценный `python-gitlab` избыточен |
| Хранение токена | `keyring` → Windows Credential Manager | токен не лежит в конфиге открытым текстом |
| Конфиг/состояние | JSON в `%APPDATA%\GetGit\` | простота, читаемость |
| Логирование | `logging` + RotatingFileHandler + вывод в окно | лог и в файл, и в UI |
| Сборка | PyInstaller (onefile, `--windowed`) | один exe, Python у пользователей не нужен |

Внешнее требование на машине пользователя: установленный **Git for Windows** и настроенный
SSH-ключ. Приложение проверяет и то и другое при старте (см. §6).

## 4. Интерфейс (главное окно)

```
┌──────────────────────────────────────────────────────────────┐
│ Директория: [D:\repos………………………] [Обзор…]      [⚙ Настройки] │
│                                    [Обновить список] [Обновить] │
├──────────────────────────────────────────────────────────────┤
│ Репозиторий        │ Группа      │ Локально │ Обновлено      │
│ backend-api        │ dev/core    │   ✔      │ 18.08.2026 09:41│
│ frontend           │ dev/web     │   ✔      │ 17.08.2026 18:02│
│ infra-scripts      │ ops         │   ✘ нет  │ —              │
│  … (QTableView, сортировка по колонкам)                      │
├──────────────────────────────────────────────────────────────┤
│ Лог операций (QPlainTextEdit, read-only, автопрокрутка)      │
│ 09:41:02 backend-api: fetch… 12 новых коммитов, 1 ветка удалена│
│ 09:41:05 infra-scripts: клонирование… готово                 │
├──────────────────────────────────────────────────────────────┤
│ [████████░░] 7 из 12          статус: синхронизация…  [Отмена]│
└──────────────────────────────────────────────────────────────┘
```

Поведение:
- **Обновить список** — запрашивает перечень проектов из GitLab API, сверяет с локальной папкой, обновляет таблицу (git-операций не делает). Выполняется также автоматически при старте.
- **Обновить** — для каждого репозитория: нет локально → клонировать; есть → синхронизировать. Кнопка блокируется на время работы, доступна «Отмена» (докатывает текущие задачи, новые не запускает).
- Диалог «Настройки»: URL GitLab, personal access token (сохраняется в Credential Manager), путь к SSH-ключу (по умолчанию `~/.ssh/id_ed25519`), число параллельных потоков.
- Дата «Обновлено» берётся из `state.json` (момент последней успешной операции по данному репо).

## 5. Ключевая логика

### 5.1 Список репозиториев (GitLab API)

- `GET {gitlab_url}/api/v4/projects?membership=true&archived=false&simple=true&per_page=100`
  с пагинацией по заголовку `X-Next-Page`; из ответа берутся `path_with_namespace` и `ssh_url_to_repo`.
- Локальный путь репозитория = `{базовая_директория}\{path_with_namespace}` (подпапки по группам —
  исключает коллизии одинаковых имён в разных группах).
- Ошибки 401/403 → понятное сообщение «токен недействителен, откройте Настройки».

### 5.2 Клонирование (первый запуск / новый репозиторий)

```
git clone --origin origin <ssh_url> <локальный_путь>
```

### 5.3 Синхронизация (полная, репозиторий уже есть)

```
git fetch origin "+refs/heads/*:refs/heads/*" --prune --tags --prune-tags --force
git reset --hard origin/<default_branch>     # обновить рабочую копию
git clean -fd                                 # убрать посторонние файлы (копия read-only)
```

Первая команда обновляет **все** локальные ветки принудительно и удаляет исчезнувшие с сервера
(refspec `+refs/heads/*:refs/heads/*` обновляет даже не checked-out ветки; для текущей ветки
рабочую копию доводит `reset --hard`). Default branch берётся из ответа API (`default_branch`).

### 5.4 SSH

Все git-команды получают окружение:

```
GIT_SSH_COMMAND=ssh -i <путь_к_ключу> -o BatchMode=yes -o StrictHostKeyChecking=accept-new
```

`BatchMode=yes` гарантирует, что ssh не зависнет на запросе пароля — вместо этого будет
ошибка в лог. Ключи с passphrase поддерживаются только через запущенный ssh-agent
(указать в README).

### 5.5 Параллельность и UI-поток

- Git-операции выполняются в `QThreadPool` (по умолчанию 4 одновременных задачи, настраивается).
- Каждая задача (`QRunnable`) шлёт сигналы: `log(строка)`, `done(repo, ok, сообщение)` —
  UI-поток обновляет таблицу и лог. Никаких git/сетевых вызовов в главном потоке.
- Таймаут на git-команду (например, 10 мин) — защита от зависших сетевых операций.

### 5.6 Конфигурация и состояние

- `%APPDATA%\GetGit\config.json` — базовая директория, URL GitLab, путь к ключу, число потоков.
- Токен — только в Windows Credential Manager (`keyring`).
- `%APPDATA%\GetGit\state.json` — по каждому репо: дата/время последней успешной синхронизации,
  результат последней операции.
- `%APPDATA%\GetGit\logs\app.log` — ротация 5 × 2 МБ.

## 6. Проверки при старте и обработка ошибок

| Ситуация | Поведение |
|---|---|
| git.exe не найден в PATH | диалог с инструкцией установить Git for Windows, работа блокируется |
| SSH-ключ отсутствует / не подходит | проверка `ssh -T git@<host>` при старте, предупреждение в лог |
| Токен не задан / истёк | открыть диалог настроек |
| Нет сети / GitLab недоступен | сообщение в лог, таблица показывает последнее известное состояние |
| Файл занят (антивирус, IDE) | ошибка по конкретному репо в лог, остальные продолжают обновляться |
| Длинные пути Windows | при клонировании передавать `-c core.longpaths=true` |
| Папка есть, но это не git-репозиторий | пометить в таблице «конфликт», не трогать без подтверждения |

Итог каждой операции по каждому репозиторию фиксируется в логе; общий результат —
«обновлено N, ошибок M» в статус-баре.

## 7. Этапы разработки

| # | Этап | Содержание | Оценка |
|---|---|---|---|
| 1 | Каркас | структура проекта, config/state, keyring, логирование, пустое окно | 1–2 дня |
| 2 | GitLab-клиент | API-клиент с пагинацией, диалог настроек, таблица со списком и статусом «локально/нет» | 1–2 дня |
| 3 | Git-операции | clone/sync через subprocess, GIT_SSH_COMMAND, пул потоков, лог в окно, прогресс, отмена | 2–3 дня |
| 4 | Устойчивость | стартовые проверки (§6), таймауты, обработка ошибок, даты обновления | 1–2 дня |
| 5 | Сборка | PyInstaller onefile + иконка, проверка на чистой машине без Python | 1 день |
| 6 | Тесты и доводка | unit-тесты core (мок API, временные локальные репо), ручное тестирование на реальном GitLab | 1–2 дня |

Итого: **~7–12 рабочих дней** до готовой версии 1.0.

## 8. Риски

- **SmartScreen/антивирус** на неподписанном PyInstaller-exe — при распространении внутри
  компании решается подписью кодовым сертификатом или добавлением в доверенные.
- **Много крупных репозиториев** — первый прогон может занять часы; смягчается параллельностью
  и, при необходимости, опцией `--depth` (shallow clone) в настройках как v1.1.
- **`git clean -fd`** удаляет любые посторонние файлы в рабочей копии — это осознанное
  следствие режима «локальная копия = зеркало сервера»; явно указать в README.

## 9. Возможные развития (вне v1.0)

- Обновление по расписанию / при старте автоматически.
- Фильтр по группам GitLab (выкачивать не всё доступное, а выбранное).
- Shallow/partial clone для экономии диска.
- Отображение размера репозитория и текущей ветки в таблице.
